---
name: Newsletter/drip-sequence module patterns
description: Durable design decisions for the Resend-based newsletter module (domains, API keys, campaigns, drip sequences) — apply when extending or reviewing similar email-sending features.
---

- **Unsubscribe links must never accept a raw email as proof of identity.** Generate a random per-subscriber `unsubscribeToken` at insert time and require it (not the email) to resolve the unsubscribe action. Otherwise anyone who knows/guesses an email can unsubscribe it.
- **Unsubscribe (or any public link inside an email body) must not mutate state on GET.** Mail security scanners and client link-prefetchers auto-request every link in a delivered email; a GET that unsubscribes will silently opt out real subscribers who never clicked anything. Split into GET (renders a confirmation page only) and POST (performs the actual mutation). POST also gives you RFC 8058 one-click-unsubscribe compatibility (`List-Unsubscribe` + `List-Unsubscribe-Post: List-Unsubscribe=One-Click` headers on the outgoing email, pointing at the POST endpoint).
- **Any URL embedded in an outbound email must be built from the environment's actual public domain resolver** (this project already has `getPublicBaseUrl()` in `artifacts/api-server/src/lib/socialService.ts`, reading `REPLIT_DOMAINS`/`REPLIT_DEV_DOMAIN`), never a config var that isn't actually wired up anywhere. If the resolver can't determine a domain, treat that as a hard failure and skip sending rather than emailing a broken link.
  - **Why:** a prior pass used an undocumented, unused `PUBLIC_BASE_URL` env var that silently fell back to a relative path — the link would resolve against the mail client's own origin, not the app.
- **Multi-step drip/retry sequences must not advance past a step whose send failed.** On send failure: keep `currentStep` unchanged, log the failure, and schedule a retry with exponential backoff capped at some ceiling; only mark the enrollment as a terminal `failed` state after a max attempt count. Advancing to the next step (or marking `completed`) on failure permanently loses that message for the subscriber, even after the underlying problem (Resend outage, unverified sending domain, etc.) is fixed.
- **API keys for external/public API access must be stored hashed (e.g. sha256), never plaintext.** Return the raw key once, at creation time, and never again; list/detail endpoints only ever show a `keyLastFour`-style hint. Auth middleware for the public API must hash the incoming key before the DB lookup.
- **New DB tables added via `lib/db/src/schema/*.ts` are not actually provisioned anywhere until a migration script exists AND is chained into the service's `start` script** (see the `migrate:social-marketing` / `migrate:newsletter` pattern in `lib/db/package.json` + `artifacts/api-server/package.json`). A schema-only change works in the dev DB (already patched by hand during development) but leaves a freshly provisioned/deployed DB completely missing the tables. Migration scripts must be idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`); unique constraints added later should be added as `CREATE UNIQUE INDEX IF NOT EXISTS` rather than `ALTER TABLE ... ADD CONSTRAINT` guarded by a `pg_constraint` existence check — drizzle's `uniqueIndex()` creates a plain unique index (not a named constraint row in `pg_constraint`), so the constraint-existence check won't detect it and the `ADD CONSTRAINT` will collide on the index name.

## 二、製作說明書（建議施工順序與步驟）

原則：先把「營運會馬上用到、且不依賴外部單位」的做完；需要外部配合（金流、發票、CIS）的先行文件確認、最後施工。（ICOPE 與外部 ERP 串接已移除，不施作——平台內建的進銷存／財務模組即為 ERP，AI 行政助理直接以其為資料來源。）

### 第 1 階段：補齊營運核心（不依賴外部）✅ 已完成（2026-08-31）

**1-1 機構共用錢包**
1. 資料庫：機構錢包主檔（機構、餘額）與交易明細（儲值/扣款/退款，含經手人）
2. 後端：批貨結帳時改扣機構錢包（限審核通過的機構成員）、餘額不足擋單；營運後台儲值/調整
3. 前端：機構後台錢包頁改為機構共用餘額與明細；營運後台機構錢包管理頁
4. 驗收：兩位同機構成員共用同一餘額；扣款、對帳明細正確

**1-2 患者綁定 × 佣金明細報表**
1. 資料庫：患者綁定紀錄（會員、機構、科室、時間）；佣金計算掛上綁定關係
2. 後端：訂單完成時依綁定關係與佣金規則入帳；報表 API 支援縣市／醫院／科室維度，逐筆明細
3. 前端：營運後台佣金報表（維度切換＋明細匯出）；機構後台「佣金對帳」頁（明細非總額）
4. 驗收：綁定→消費→佣金入帳→機構可核對每一筆

**1-3 知識內容管理（CMS）**
1. 資料庫：文章加審核狀態、版本紀錄、關聯商品
2. 後端：營運後台文章／FAQ／公告的建立、編輯、送審、上下架 API
3. 前端：營運後台「知識內容」模組（編輯器、審核流、版本）
4. 驗收：非工程人員可自行上稿、審核、上下架（此模組同時是日後 AI 客服的知識庫來源）

**1-4 角色權限細分**
1. 角色擴充：系統管理員／營運／客服／機構，各自可視範圍
2. 後端：權限中介層依角色限制 API；前端後台選單依角色顯示
3. 驗收：客服帳號看不到財務；營運看不到系統設定

### 第 3 階段：AI 大腦（行政助理＋衛教客服，共用 RAG 基礎）✅ 已完成（2026-09-01）

> 施工結果：3-1／3-2／3-3 全數上線。知識庫索引涵蓋商品、訂單、會員、機構、文章、公告、佣金，資料異動即自動同步，並提供管理員一鍵全量重建。行政助理採「兩段式確認」——AI 先建立待確認操作（單次有效、10 分鐘時效），管理者於下一則訊息明確同意後才會真正執行，全程留存稽核紀錄；機構錢包儲值僅限系統管理員。衛教客服僅引用已發佈內容並附來源，涉及診斷／用藥自動轉真人，後台客服對話中心可接手回覆與結案。目前檢索為關鍵字模式；提供 OpenAI 金鑰後可升級為向量語意檢索（介面已就緒）。

**3-1 資料向量化基礎（RAG 底層，兩個 AI 共用）**
1. 建立向量資料庫（pgvector）：全站資料自動同步成向量索引——商品、訂單、會員、機構、庫存異動、錢包／佣金、進銷存、財務、CMS 內容
2. 同步機制：資料新增／修改即自動更新索引（含歷史資料一次性回填）；日後所有新建立的內容都自動進入 AI 知識庫
3. 權限邊界：向量檢索遵守角色權限（客服查不到財務、機構只看自己的資料）

**3-2 AI 行政助理（後台最大的原始大腦）**
1. 定位：營運後台的聊天式操作中樞，管理者用對話即可完成後台所有工作，等同內部 ERP 的智慧入口
2. 查詢（內建 ERP 數據）：進銷存、財務、訂單等 ERP 資料都在後台，AI 直接讀取，用自然語言查任何資料——「上個月哪家醫院佣金最高？」「益生菌大盒裝還剩多少庫存？」「幫我列出未出貨超過三天的訂單」
3. 操作：透過對話建立訂單、調整庫存、處理訂單狀態、儲值機構錢包、上架文章等；每筆操作先向管理者確認再執行，並完整留存操作紀錄
4. 會報統計：對話產出彙總報表（銷售、佣金、庫存、財務），可依期間／機構／商品維度即時統整分析
5. 流程管理：AI 主動提示待辦——待審核綁定、低庫存、待出貨訂單、草稿文章等
6. 前端：後台專屬 AI 助理對話框（常駐側欄），支援追問與上下文
7. 權限：僅系統管理員／營運可使用完整功能；操作類指令依角色權限把關

**3-3 AI 衛教客服（會員端）**
1. 知識庫：以 CMS 已發佈內容為來源（共用 3-1 的向量索引）
2. 後端：意圖判斷→語意檢索→LLM 生成回覆並附來源；信心不足或涉及診斷／用藥自動轉真人並提示「請洽醫師或合作醫院」
3. 前端：App 內客服對話介面；真人客服接手介面（客服角色使用）
4. 合規：回覆用語避免療效宣稱（食藥署廣告規範）；對話紀錄留存稽核
5. 之後再擴充 LINE 官方帳號、官網入口（同一套客服系統）

## 四、商城後台與 ERP 職責劃分（2026-09-01 完成）

隨著 ERP（七期生醫 ERP）已補齊完整的進銷存、採購、報價單、會計模組，商城後台（七期生醫採購平台）與 ERP
一度有多處功能重複、甚至共用同一張資料表卻各自維護 UI，容易互相打架。本次調整明確劃分兩邊職責：

### 4-1 商城後台現在只保留

- 商品內容管理（名稱、圖片、文案、售價、分級授權）——**庫存數字改為唯讀顯示**，實際庫存以 ERP 各倉庫存為準
- 訂單管理、會員／機構主檔（登入身份與分級授權）
- 行銷：社群貼文、電子報／滴灌式行銷、Linktree
- 內容管理（衛教文章／公告）、客服對話、AI 助理、儀表板
- 會員錢包、機構共用錢包、分潤／佣金（商城獨有的會員獎勵機制，非一般會計科目）

### 4-2 已從商城後台移除、統一改由 ERP 負責

以下頁面已從商城後台刪除（前端頁面與選單），對應功能請一律至 ERP 操作：

| 移除的商城後台頁面 | 現在請至 |
|---|---|
| 進銷存總覽／異動紀錄 | ERP「庫存管理」 |
| 進銷存報表 | ERP「銷售/採購分析」「帳齡分析」等報表 |
| 採購進貨（此頁送出動作原本已停用） | ERP「採購管理」 |
| 報價單管理（與 ERP 共用同一張資料表） | ERP「報價單」 |
| 財務管理（簡易損益） | ERP「會計」完整模組（科目、傳票、發票、銀行對帳、財務報表） |

### 4-3 庫存雙重帳修復——現在只有一本真帳

過去 `products.stock` / `product_variants.stock`（商品主檔上的舊制庫存欄位）與 ERP 的
`warehouse_stock`（各倉庫存，真正決定「商城能不能賣」）是各自獨立維護的兩本帳，任何一條扣庫存或
補庫存路徑（結帳、取消、退貨、採購收貨、ERP 銷貨、盤點調整、跨倉調撥、AI 助理代客下單／調整庫存）
只要漏更新其中一本，兩邊數字就會兜不起來。

修復後的規則：
- **唯一真實數字＝ERP 各倉庫存（warehouse_stock）加總**，所有「庫存夠不夠、能不能扣」的判斷都只看這裡。
- 商品主檔上的舊制庫存欄位保留（沒有刪除資料表欄位，相容既有讀取路徑），但改成**唯讀鏡像**——
  每次分倉庫存異動完成後，系統自動把「各倉加總」寫回這個欄位供顯示與搜尋使用，本身不再參與任何判斷或獨立增減。

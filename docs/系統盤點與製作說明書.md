## 二、製作說明書（建議施工順序與步驟）

原則：先把「營運會馬上用到、且不依賴外部單位」的做完；需要外部配合（金流、發票、ICOPE、ERP、CIS）的先行文件確認、最後施工。

### 第 1 階段：補齊營運核心（不依賴外部）

**1-1 機構共用錢包**
1. 資料庫：機構錢包主檔（機構、餘額）與交易明細（儲值/扣款/退款，含經手人）
2. 後端：批貨結帳時改扣機構錢包（限審核通過的機構成員）、餘額不足擋單；營運後台儲值/調整
3. 前端：機構後台錢包頁改為機構共用餘額與明細；營運後台機構錢包管理頁
4. 驗收：兩位同機構成員共用同一餘額；扣款、對帳明細正確

**1-2 患者綁定 × 佣金明細報表**
1. 資料庫：患者綁定紀錄（會員、機構、科室、時間）；佣金計算掛上綁定關係
2. 後端：訂單完成時依綁定關係與佣金規則入帳；報表 API 支援縣市／醫院／科室維度，逐筆明細
3. 前端：營運後台佣金報表（維度切換＋明細匯出）；機構後台「佣金對帳」頁（明細非總額）
4. 驗收：綁定→消費→佣金入帳→機構可核對每一筆

**1-3 知識內容管理（CMS）**
1. 資料庫：文章加審核狀態、版本紀錄、關聯商品
2. 後端：營運後台文章／FAQ／公告的建立、編輯、送審、上下架 API
3. 前端：營運後台「知識內容」模組（編輯器、審核流、版本）
4. 驗收：非工程人員可自行上稿、審核、上下架（此模組同時是日後 AI 客服的知識庫來源）

**1-4 角色權限細分**
1. 角色擴充：系統管理員／營運／客服／機構，各自可視範圍
2. 後端：權限中介層依角色限制 API；前端後台選單依角色顯示
3. 驗收：客服帳號看不到財務；營運看不到系統設定

### 第 2 階段：出貨存證與商品架構

**2-1 出貨照片存證**
1. 建立雲端檔案儲存（物件儲存）
2. 後端：出貨紀錄（照片、物流單號、時間）、照片上傳 API
3. 前端：營運後台出貨作業頁（拍照/上傳→出貨）；會員/機構端訂單頁顯示出貨照片與物流單號

**2-2 商品多規格／變化品**
1. 資料庫：商品規格（SKU）層：包裝、規格、組合品，各自價格與庫存
2. 後端：購物車、訂單、庫存、進銷存全面改為以 SKU 計算
3. 前端：商品頁規格選擇器；後台商品編輯支援多規格
4. 註：影響面最大的一項，需完整迴歸測試（購物車→結帳→庫存→報表）

**2-3 授權可銷售機構範圍＋機構分級主檔**
1. 機構主檔加分級（A/B/C）；商品設定可銷售機構範圍
2. 商城依登入者所屬機構過濾可購商品

### 第 3 階段：AI 衛教客服（RAG）

1. 知識庫：以 CMS 內容建立向量索引（pgvector），內容須經審核才進知識庫
2. 後端：意圖判斷→語意檢索→LLM 生成回覆並附來源；信心不足或涉及診斷／用藥自動轉真人並提示「請洽醫師或合作醫院」
3. 前端：App 內客服對話介面；真人客服接手介面（客服角色使用）
4. 合規：回覆用語避免療效宣稱（食藥署廣告規範）；對話紀錄留存稽核
5. 之後再擴充 LINE 官方帳號、官網入口（同一套客服系統）

### 第 4 階段：對外串接（需外部單位配合，先取規格文件）

| 項目 | 前置確認 | 施工內容 |
|---|---|---|
| 第三方金流（綠界/藍新） | 商家申請、是否需儲值代收牌照 | 線上刷卡/ATM；機構錢包儲值改走金流 |
| 電子發票 | 加值服務商選定、開立範圍 | 訂單開立發票、作廢折讓、佣金憑證 |
| LINE 登入/官方帳號 | LINE 開發者帳號 | 快速登入綁定既有帳號、客服入口 |
| ICOPE | 院方 IT 確認 API 範圍與資安 | 回診提醒→衛教推播等同步，留存同步紀錄 |
| ERP（銷售/會計） | 取得 API 技術規格文件 | 訂單過帳、應收應付、佣金費用認列之雙向同步 |
| CIS 套版 | 客戶提供素材 | 前台品牌視覺全面套版 |

### 第 5 階段：上架與強化

1. 原生 App：以現有系統為基礎包裝 iOS/Android App 上架
2. 點數機制：消費累點、折抵規則
3. 高可用與容量：依實際機構數量與流量調整資料庫與快取（Redis）
4. 經營報表持續優化

## 三、待確認事項（影響時程，建議盡早確定）

1. 機構錢包儲值是否需第三方支付牌照，或沿用匯款入帳＋人工核帳
2. 佣金撥付是否需開立憑證（與財會確認）
3. 電子發票開立範圍（全部訂單或特定通路）
4. ERP API 規格文件、ICOPE 介接範圍（外部單位）
5. CIS 素材提供時間
6. 出貨照片保留年限（影響儲存空間規劃）
